## 主張

出典のリンクは原論文PDFの該当ページを開く。リンクにカーソルを合わせると原文の引用が表示される。

- **c1** Routing decision: before any LLM is called, a win-prediction model estimates the probability that the strong model beats the weak model on the query, and the query goes to the strong model when this probability is at least a cost threshold alpha; a higher alpha favours the weak model (stricter cost), a lower alpha favours the strong model. Each query is sent to a single LLM.([Problem formulation, p.3](https://arxiv.org/pdf/2406.18665v4#page=3 "The threshold α controls the trade-off between quality and cost: a higher value of α enforces stricter cost constraints by favoring weak models more often, while a lower α biases toward higher-quality (but more expensive) strong models."))
- **c2** Training signal: the primary preference data are 80k Chatbot Arena battles in which users vote between two anonymous models; to reduce label sparsity, models are clustered into 10 tiers by Arena leaderboard score, the top two tiers form the strong class and the third tier the weak class, and only winner identities (not responses) are kept.([Chatbot Arena data, p.4](https://arxiv.org/pdf/2406.18665v4#page=4 "Our primary source for preference data is the 80k battles from the online Chatbot Arena platform (Chiang et al., 2024), where users submit prompts and receive responses from two anonymous models."))
- **c3** Cost/quality metrics and thresholds: cost is measured as the percentage of calls to the strong model and quality relative to the weak-strong gap (performance gap recovered, PGR); APGR averages PGR over 10 discretized call percentages, choosing for each the threshold that satisfies that cost constraint, and CPT(x%) is the minimum percentage of strong-model calls needed to reach a PGR of x%. The text does not say on which data the thresholds for each call percentage are determined.([Metrics, p.4](https://arxiv.org/pdf/2406.18665v4#page=4 "For each ci, we determine the threshold αi that satisfies the cost constraint."))
- **c4** Evaluation protocol: MMLU, MT Bench (LLM-as-a-judge) and GSM8K, after discarding evaluation examples flagged by an embedding similarity search against the training data with a threshold of 0.95 (Appendix B); the authors present these public benchmarks as a test of out-of-domain generalization; main strong/weak pair gpt-4-1106-preview / Mixtral 8x7B; the baseline is a random router under the same cost constraint; BERT and causal-LLM routers use 5k samples held out from the Arena data as a validation set for model selection.([Experiments, p.6](https://arxiv.org/pdf/2406.18665v4#page=6 "MMLU (Hendrycks et al., 2020) consisting of 14,042 questions across 57 subjects, MT Bench (Zheng et al., 2023) with 160 open-ended questions using LLM-as-a-judge, and GSM8K (Cobbe et al., 2021) with over 1,000 grade school math problems"))
- **c5** Failure under query-distribution shift: routers trained only on Arena data perform at the level of the random router on MMLU (and close to random on GSM8K), which the authors attribute to most questions being out-of-distribution; adding about 1500 golden-labeled questions from MMLU's own validation split (for MMLU; i.e. in-domain data for that benchmark) or the roughly 120K GPT-4-judge labels on Nectar queries (for GSM8K) brings them above random. The authors relate router quality to an embedding-based benchmark-dataset similarity score.([Results, p.8](https://arxiv.org/pdf/2406.18665v4#page=8 "On MMLU (Table 2), all routers perform poorly at the level of the random router when trained only on Arena dataset, which we attribute to most MMLU questions being out-of-distribution (see Section 5.3)."))
- **c6** Generalization to unseen model pairs: the same routers (trained on Arena + judge data) are applied without retraining to Claude 3 Opus / Claude 3 Sonnet and Llama 3.1 70B / Llama 3.1 8B, which are not in the training data (the judge-labeled augmentation data compare GPT-4 and Mixtral responses); the authors report performance on MT Bench comparable to the original pair and significantly stronger than random. This transfer test is reported on MT Bench only, not on MMLU or GSM8K.([Adaptability across models, p.8](https://arxiv.org/pdf/2406.18665v4#page=8 "Importantly, we use the same routers as before without any retraining, and only replace the strong and weak model routed to."))
- **c7** Stated limitations: real-world query distributions may differ substantially from the evaluated benchmarks (the authors suggest collecting a small amount of in-domain data for augmentation); only two-model routing is studied; and performance of different routers trained on the same data can vary widely on the same benchmark without a clear explanation.([Conclusion, p.10](https://arxiv.org/pdf/2406.18665v4#page=10 "First, although we evaluate on a diverse set of benchmarks, real-world applications may have distributions that differ substantially from these benchmarks."))
